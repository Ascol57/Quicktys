# Traductions

Chaque « chose » de Quicktys porte ses propres traductions. Le cœur, chaque
plugin, chaque module, chaque widget. C'est décentralisé volontairement, et c'est
le principal écart avec la façon dont CastMate gérait les locales.

## La règle

> **Un manifeste émet des clés. Il n'émet jamais de texte traduit.**

Si vous écrivez `.named("Qui")` dans un manifeste, cette chaîne est intraduisible
pour toujours. Écrivez `.named("plugin.greeter.fields.who")` et mettez l'anglais
dans `lang/en.json`.

Le host n'émet pas non plus de texte traduit — il transmet au frontend des clés et
des bundles de locale, et la résolution se fait dans l'UI.

## Le dossier `lang/`

```
lang/                  → le cœur / la coquille    → namespace  core.*
plugins/<id>/lang/     → un plugin                → namespace  plugin.<id>.*
modules/<id>/lang/     → un module                → namespace  module.<id>.*
widgets/<id>/lang/     → un widget                → namespace  widget.<id>.*
```

Un fichier JSON par locale — `en.json`, `fr.json`, `de.json`, `es.json`,
`pt.json`. Le host découvre le dossier au chargement de l'extension, namespace le
bundle par l'id de l'extension, et le pousse au frontend avec le manifeste.

**`en.json` est la locale de référence.** Une clé absente d'une autre locale y
retombe, donc une traduction partielle est acceptable et utile.

## Les locales sont des données

Le dossier `lang/` voyage **à côté** du `.wasm`, dans le bundle. Il n'est jamais
compilé dans le composant.

Trois conséquences qui justifient le choix :

- un traducteur n'a besoin ni de chaîne Rust ni de build ;
- un utilisateur peut éditer ou surcharger une traduction localement ;
- ajouter une langue à une extension existante revient à ajouter un fichier.

## Structure

Reflétez la structure de clés de votre manifeste.

### Un plugin

```json
{
  "name": "Countdown",
  "description": "Named countdown timers, driven from automations.",
  "fields": {
    "name": "Countdown"
  },
  "actions": {
    "start": {
      "name": "Start countdown",
      "description": "Start (or restart) a countdown for the given duration.",
      "config": {
        "duration": "Duration",
        "label": "Label"
      }
    },
    "pause": { "name": "Pause countdown" }
  },
  "triggers": {
    "finished": {
      "name": "Countdown finished",
      "description": "Fires when a countdown reaches zero.",
      "context": {
        "name": "Countdown",
        "label": "Label"
      }
    }
  },
  "state": {
    "timer": { "name": "Timer" }
  },
  "settings": {}
}
```

Résolu en `plugin.countdown.actions.start.name`, et ainsi de suite.

::: tip Une section `fields` partagée
Plusieurs actions partagent en général les mêmes libellés de champ. Mettez-les
dans un `fields` de premier niveau et pointez plusieurs schémas vers la même clé —
c'est ce que font les plugins OBS et Twitch, et ça garde lisible le fichier de
locale d'un plugin à trente actions.
:::

### Un module

```json
{
  "name": "HTTP",
  "description": "Generic HTTP(S) requests for plugins.",
  "services": { "request": { "name": "HTTP request" } },
  "events": { "response": { "name": "Response" } }
}
```

### Un widget

```json
{
  "name": "Countdown",
  "config": {
    "format": "Format",
    "showLabel": "Show label"
  },
  "options": {
    "format": { "auto": "Automatic", "mm:ss": "Minutes and seconds" }
  }
}
```

::: warning Les libellés d'énumération ne sont pas sous `config`
`widget.<id>.config.<clé>` doit rester une **chaîne** — c'est le libellé du champ
lui-même. Les libellés d'options vivent sous
`widget.<id>.options.<clé>.<valeur>`. Une clé qui résout vers un objet casse la
résolution de traduction à l'exécution.
:::

## Côté frontend

La résolution passe par `vue-i18n` :

```js
$t("plugin.countdown.actions.start.name")
```

Les pages isolées — une iframe de widget, une vue contribuée par un module —
**n'ont pas accès à l'i18n de l'app**. Le host résout leurs libellés et les livre
dans le message d'initialisation (`label`, `configLabels`, `optionLabels`). Si
vous écrivez l'une de ces pages, lisez les libellés depuis le message plutôt que
d'essayer de traduire.

## Ajouter une langue à une extension existante

1. Copiez `lang/en.json` en `lang/<locale>.json`.
2. Traduisez les valeurs, en laissant les clés telles quelles.
3. Reconstruisez le bundle (pour un widget, ce n'est qu'une copie).

Pas de Rust, pas de recompilation du composant, pas de coordination avec l'auteur
de l'extension au-delà d'une pull request.

## Le texte à l'exécution

La localisation est par défaut une affaire de frontend. Si une extension devait un
jour *produire* du texte localisé à l'exécution plutôt que de libeller son UI, une
capacité host `i18n.translate(key)` serait ajoutée — elle n'existe pas
aujourd'hui.

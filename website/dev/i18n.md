# Translations

Every "thing" in Quicktys carries its own translations. The core, each plugin,
each module, each widget. This is decentralised on purpose, and it is the main
departure from how CastMate handled locales.

## The rule

> **A manifest emits keys. It never emits translated text.**

If you write `.named("Who")` in a manifest, that string is untranslatable
forever. Write `.named("plugin.greeter.fields.who")` and put the English in
`lang/en.json`.

The host never emits translated text either — it hands the frontend keys and
locale bundles, and resolution happens in the UI.

## The `lang/` folder

```
lang/                  → the core / app shell   → namespace  core.*
plugins/<id>/lang/     → a plugin               → namespace  plugin.<id>.*
modules/<id>/lang/     → a module               → namespace  module.<id>.*
widgets/<id>/lang/     → a widget               → namespace  widget.<id>.*
```

One JSON file per locale — `en.json`, `fr.json`, `de.json`, `es.json`, `pt.json`.
The host discovers the folder when it loads the extension, namespaces the bundle
by the extension's id, and pushes it to the frontend with the manifest.

**`en.json` is the reference locale.** A key missing from another locale falls
back to it, so a partial translation is fine and useful.

## Locales are data

The `lang/` folder travels **beside** the `.wasm` inside the bundle. It is never
compiled into the component.

That has three consequences worth the design:

- a translator needs no Rust toolchain and no build;
- a user can edit or override a translation locally;
- adding a language to an existing extension is adding a file.

## Structure

Mirror your manifest's key structure.

### A plugin

```json
{
  "name": "Countdown",
  "description": "Named countdown timers, driven from automations.",
  "fields": {
    "name": "Countdown"
  },
  "actions": {
    "start": {
      "name": "Start countdown",
      "description": "Start (or restart) a countdown for the given duration.",
      "config": {
        "duration": "Duration",
        "label": "Label"
      }
    },
    "pause": { "name": "Pause countdown" }
  },
  "triggers": {
    "finished": {
      "name": "Countdown finished",
      "description": "Fires when a countdown reaches zero.",
      "context": {
        "name": "Countdown",
        "label": "Label"
      }
    }
  },
  "state": {
    "timer": { "name": "Timer" }
  },
  "settings": {}
}
```

Resolved as `plugin.countdown.actions.start.name`, and so on.

::: tip A shared `fields` section
Several actions usually share field labels. Put them under a top-level `fields`
and point several schemas at the same key — that is what the OBS and Twitch
plugins do, and it keeps a 30-action plugin's locale file readable.
:::

### A module

```json
{
  "name": "HTTP",
  "description": "Generic HTTP(S) requests for plugins.",
  "services": { "request": { "name": "HTTP request" } },
  "events": { "response": { "name": "Response" } }
}
```

### A widget

```json
{
  "name": "Countdown",
  "config": {
    "format": "Format",
    "showLabel": "Show label"
  },
  "options": {
    "format": { "auto": "Automatic", "mm:ss": "Minutes and seconds" }
  }
}
```

::: warning Enum labels are not under `config`
`widget.<id>.config.<key>` must stay a **string** — it is the field's own label.
Option labels live under `widget.<id>.options.<key>.<value>`. A key that resolves
to an object breaks translation lookup at runtime.
:::

## In the frontend

Resolution goes through `vue-i18n`:

```js
$t("plugin.countdown.actions.start.name")
```

Sandboxed pages — a widget iframe, a module's contributed view — have **no access
to the app's i18n**. The host resolves their labels and ships them in the init
message instead (`label`, `configLabels`, `optionLabels`). If you are writing one
of those, read the labels from the message rather than trying to translate.

## Adding a language to an existing extension

1. Copy `lang/en.json` to `lang/<locale>.json`.
2. Translate the values, leaving the keys alone.
3. Rebuild the bundle (for a widget, that is just a copy).

No Rust, no rebuild of the component, no coordination with the extension author
beyond a pull request.

## Runtime text

Localisation is a frontend concern by default. If an extension ever needs to
*produce* localised text at runtime rather than label its UI, a host
`i18n.translate(key)` capability would be added — it does not exist today.
